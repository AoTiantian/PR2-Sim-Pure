## 一、项目是什么

MuJoCo + ROS 2 Jazzy 仿真：**虚拟人（弹簧阻尼阻抗程序）与 PR2 机器人协同搬运一块 2 m 长板**。对比两种条件：纯人（human_only）vs 人机（human_robot，PR2 纯力随动导纳控制）。核心研究问题：加入机器人后，人是否在跟踪质量不降的前提下减负。

**核心实验原则（9.26 新确认，务必遵守）**：机器人必须保持**纯被动**——只能根据测到的腕部力/力矩反应，绝不能给它任何关于人的期望轨迹/意图的信息。9.26 我在 QP 里打开过一个现成但一直关闭的 `orientation_tracking_enable` 分支做"姿态辅助"实验，效果是好的（S12 偏航差距从 26° 缩到 9°），但用户明确否决并要求撤回——研究问题是"机器人只靠触觉能不能协作"，一旦让机器人看见参考轨迹就变成了另一个问题。**以后任何会让机器人获知人的期望轨迹/姿态/位置目标的改动，都要先明确提出讨论，不能直接做。** `contract_guard.py` 里的 `orientation_tracking_enable=False` 等断言就是在强制这个契约，改契约前先确认是不是真的要改变实验设计。

## 三、9.26 新确认的结论（全部有实验证据，按主题分组）

### 3.1 "10 Hz 涌现支撑力" —— 彻底证伪，别再引用

9.25 版文档里"指令转发 10 Hz 在软轮伺服下曾涌现 ~9.5-12.9 N 平均支撑"这条，9.26 用独立数据管道重新验证：
- 对 `robot_cmd_rate_hz ∈ {100,50,20,10,5}` 各跑 3 次干净重复（含一次因后台进程重叠导致数据污染、已全部丢弃重跑），腕部 Z 向力均值在所有频率下都在 **-0.05~-0.3 N**，跟频率无关，跟旧代码 6 次重复的存档数据（`results/oldcode_repro/`，均值 -0.15~-0.24 N）几乎逐位吻合。
- **真实、可复现、但和"支撑力"无关的新发现**：100 Hz 下腕部 Z 向力有一个约 5.2 Hz 的强振荡（3 次重复功率占比 13%~56%），降到 ≤50 Hz 后消失（≤0.3%）。振荡同时出现在人手位置里、但不出现在机器人手臂关节速度里，判断是人端弹簧+机器人导纳耦合的共振模态，通过刚性板传到腕部读数，机制细节未验证（只到"数据支持这个假设"程度）。
- 用户已确认：`robot_cmd_rate_hz` 默认 10 Hz **永久保留**，不再是"为复刻现象服务的临时值"。

### 3.2 `cmd_vel_linear_gain` bug —— 已修复并转正（工作区改动之一）

- 根因：`pr2_mujoco_bridge` 把 `cmd_vel` 换算成轮子角速度的系数，`transport_comparison.launch.py` 一直没设，吃节点默认值 2.0，隐含轮子半径约 0.5 m，但真实网格半径约 0.079 m，指令速度被打了 8.5 折。项目里另外两个 launch 文件早就设成了 17.0，唯独这个对比实验用的 launch 文件没有。
- 验证：裸底盘阶跃测试确认 gain=2.0 时轮子力矩只用到额定值的 1/3 不到，速度却只达到指令的 1/6~1/10；gain=17.0 时轮子力矩才真正打到上限、速度也追上指令。真实 human_robot 任务里 X 向位置 RMSE 从 ~0.11 m 降到 ~0.065~0.072 m（3 次重复稳定），降了约 40%。
- **已转正**：`transport_comparison.launch.py` 里 `cmd_vel_linear_gain: 17.0` 现在是永久默认值（非 TEMP 状态）。

### 3.3 X 向平动残差 —— 定位到"系统性延迟"，但没找到单点根因

修完 gain 之后，X 向 RMSE 还是纯人条件（0.0015 m）的 40~50 倍，滞后约 0.84~0.98 秒。9.26 逐个测试排除：
- 转向/轮子扭矩不够 → 排除（转向 ±6.5→±30、轮子 ±7→±20 分别测过，单独松绑一个反而让另一个负担更重，整体没有实质改善）。
- `robot_cmd_rate_hz` 10→100 → 排除（100 Hz 时 RMSE、滞后、两个执行器饱和占比反而全部更差）。
- 转向角速率软件限幅 2.0→8.0 rad/s → 排除（转向饱和占比 44%→45%，毫无变化，说明瓶颈根本不是这个软件限幅）。
- **判断**：残差是 QP(100Hz) + 导纳动态 + CTC 积分 + 方向低通滤波器叠加出来的系统性延迟，不是某个可调参数。要精确拆解需要给链路每一环打时间戳做插桩，9.26 没有做（之前提议过，用户当时没有要求继续）。

### 3.4 姿态自由度：短轴翻转（Y）是稳态设计误差，长轴滚转（X）是欠阻尼共振，偏航（Z）是平动残差的投影

- **板子几何**：`size="1.0 0.050 0.020"` → 整块 2.0m(长) × 0.10m(宽) × 0.04m(厚)，初始姿态长轴对齐世界 X 轴。人手抓握点在偏离质心 1 米处（`hand_offset=[1,0,0]`）。
- **Y 轴（绕板宽/短轴，"跷跷板"式翻转）**：纯人条件下稳定在 ~0.044 rad，是设计性稳态误差——人手支撑力矩（`task_torque`，主动闭环输出）和自然力矩（`natural_moment = offset × force`，抓握偏移的几何副作用）在该值上精确打平（两者数值相等、符号相反，误差 <0.001）。这个偏差不会自己消失，只要还托举、还偏移抓握点就会存在，属于纯阻抗设计的固有特性。
- **X 轴（绕板长轴，滚转）**：温和轨迹（sinusoid）下有明显尖峰但能稳住；S12 这种快速大幅转体动作下会被强烈激振：
  - `angular_stiffness` X=100 时，纯人条件在 t≈25.5s（转体刚做完）MuJoCo QACC 发散崩溃（2 次独立复现，一致）。
  - **已验证有效的修复**：`angular_stiffness` X 改回 30（是 9.25 版就验证过的值，9.26 之前被临时改回 100 用来复刻已证伪的"cmd10hz 现象"，现在复刻目的已经不存在，理应改回）。改回 30 后 S12 纯人条件完整跑完，最终转角 181.6°（几乎完美），滚转峰值降到 1.08 rad（原来是发散，量级不可比）。
  - 继续降到 15 **没有更好**：滚转峰值反而涨到 1.83 rad——K_x=30 是目前测出的最优点，不要再往下调。
  - 拉长转弯时间（22s→44s，角速度减半）**对纯人这条路没用**：不崩溃了，但滚转峰值从 0.30（崩溃前）涨到 1.18 rad，是把"看得见的崩溃"换成了"更大但不发散的振荡"，不是真正修复。
  - **阻尼不能加大**——文档记录过 0.8/5.0 都自激发散，是 500Hz 离散回路+传输延迟决定的稳定裕度上限，9.26 没有重测，沿用旧结论。
- **Z 轴（偏航）**：
  - 人机条件下，即使是**纯平动**任务（S11，三轴期望转动全程为 0），偏航也会随时间持续累积漂移，峰值达 0.145 rad（约 8.3°），3 次独立重复完全一致；同一轨迹纯人条件下偏航只有 0.0006 rad（噪声水平），相差约 250 倍。
  - **根因已验证**：机器人抓握点（由板质心+姿态反算）在 Y 方向的跟踪误差峰值达 0.35 m，人手端只有 0.06 m，相差近 6 倍；用刚体几何反算所需偏航角（arcsin(0.29/2)≈0.145 rad）和实测峰值几乎完全一致。板子是刚性连接，机器人这一端跟不上（就是 3.3 节那个系统性延迟），两端"一头准一头拖"，只能靠板子转向去吃掉这个差距——**这不是独立问题，是 3.3 节延迟问题在偏航自由度上的投影**。
  - S12（180° 掉头）人机条件下同理：最终只转到 153.6°（差 26.4°），且拉长转弯时间到 2 倍**完全没有改善**（差距仍是 153.52° vs 44s 前的 153.56°，几乎不变）——这进一步证明它不是"给更多时间就能追上"的普通延迟，更像某种和转弯快慢无关的比例性结构衰减。
  - **重要口径提醒**：目标轨迹描述的是**人手抓握点**该在哪（`board_position + rotation @ hand_offset`），不是板子质心。板子质心和姿态都是被动结果，控制器从不直接考核它们——这也是为什么"平动时莫名其妙转起来"在这个设计里是完全可能发生的。

### 3.5 底盘 cmd_vel→轮子映射的一个真实执行缺陷（已发现，修复未成功，代码待处理）

- **发现**：`pr2_sim_ros.py::_apply_cmd_vel_to_ctrl` 原逻辑是 `if 有平动: ... elif 有转动: ...`——**只要平动分量不为零，转动分量 wz 会被整个丢弃，完全不执行**。用 `verify_logger2.py` 记录 S12 期间的 `/cmd_vel`：QP 请求的底盘总转角积分值 ≈47°，但底盘实际只转了 ≈1.1°，100% 的指令帧都是"同时有平动又有转动"。这是纯执行层的 bug，机器人依然只根据测到的力反应（wz 本身来自腕部力矩），不违反纯被动原则。
- **尝试的修复**：改写成逐脚轮完整运动学（每个脚轮速度 `v_i = v + wz×r_i`，各自算转向角和轮速，平动转动同时执行），旧函数保留为 `_apply_cmd_vel_to_ctrl_legacy` 未接入，新函数替换原名生效。
- **测试结果：变差，不能用**——S12 人机条件下最终转角从 153.6°（原逻辑）掉到 136.0°（差距从 26.4°扩大到 44.0°），滚转峰值从 0.330 涨到 0.850 rad（几乎翻 3 倍）。单次运行，未重复验证，但方向和预期相反、差距明显，判断新代码本身有问题。
- **怀疑的原因（未验证）**：门控逻辑照搬了原来"四个脚轮共享同一个转向角"时代的写法，取四个脚轮里最大对齐误差去统一限制全部轮速。纯平动时四个脚轮目标转向角相同，几乎不会不对齐；现在同时转动+平动，四个脚轮目标转向角天然不同，导致几乎每一时刻都有至少一个脚轮判定"未对齐"，触发整体门控打折甚至清零，比原逻辑更卡顿。
- **下一步建议**：把门控逻辑改成逐脚轮独立判定（每个脚轮只根据自己的对齐误差决定自己的轮速），而不是共享一个标量系数，再重新测试。**这个方向本身（底盘该同时执行平动转动）逻辑上是对的，只是门控实现需要改**，接手的人可以直接从这里继续，不需要重新调查根因。

## 六、陷阱清单（9.25 版仍然有效，9.26 新增以下几条）

1. **机器人纯被动原则**（本文第一节已强调）：任何给机器人参考轨迹信息的改动都要先明确讨论，不能直接做，`contract_guard.py` 是这个契约的强制点。
2. **同一会话里"切配置"和"跑仿真"务必分成两个独立、可验证的步骤**：9.26 出过一次事故——把 `sed` 切换 yaml 和 `ros2 launch` 绑在同一条命令里，命令被工具权限拦截后不知道是否执行到一半，重试时只重跑了 launch 部分，导致误以为跑的是 S12、实际跑的是上一个未清空的 sinusoid 配置，一份分析结论作废重来。**每次切换 `trajectory.active` 或其他实验条件后，先用 Read 工具单独确认改动生效，再单独执行仿真命令。**
3. **同一会话内可能有多个后台仿真实例互相串话题**：9.26 也出过一次——后台批量脚本没有真正结束（进程判断依据不准确），另外手动补跑了同名 trial，两个仿真实例在同一 ROS domain 里跑，导致崩溃和数据异常。每次新跑之前用 `ps aux | grep pr2_` 或 `ros2 node list` 确认干净，跑完立即用 `git diff --stat` 确认所有临时改动（yaml/launch 参数）都已按预期还原。
4. **`robot_force_z`/`robot_wrist_wrench` 是 tare 参照诊断量，不是真实支撑力**：算真实静力学支撑要用"板重 − 人端力"反算，不能直接读腕力传感器数值（9.25 版就提过，9.26 反复验证过，仍然成立）。
5. **单次运行不作数，反复出现的坑**：本次会话里 3.5 节的负面结果、3.4 节的滚转数据都只做了 1 次，写在这里的时候已经如实标注"未重复"，接手人如果要引用这些数字做结论，先补重复实验。
